Guide and glossary

Help

MailPosture turns mail-security records and reports into a prioritized, read-only status view.

Getting started

  1. Add domains.Open Settings and add every domain that appears after the @ in your organization’s From addresses.
  2. Add selectors and endpoints.Edit each domain to add the DKIM selectors used by its senders and the TLS services whose certificates should be monitored.
  3. Review the dashboard.Start with the master score and attention list, then open a domain to inspect evidence and the next recommended action.
  4. Resolve and recheck.Make DNS or service changes outside MailPosture, allow them to propagate, then select Run checks.
Checks

What MailPosture evaluates

DMARC

Checks whether the domain publishes one valid DMARC policy, its enforcement level, coverage percentage, and aggregate-report destination.

SPF

Checks for exactly one SPF record, expands include and redirect references, detects invalid or unsafe mechanisms, counts DNS-querying terms against the limit of 10, and identifies softfail or policies that authorize every sender.

DMARC aggregate reports

Shows message volume, separate alignment rates for messages that passed and failed DMARC, stacked daily results, top failing sources, and the receiving services that supplied reports. A failed-message count here does not imply that a matching RUF report exists.

Individual DMARC failure reports (RUF)

Counts optional, message-level reports sent by some receiving providers. This count is separate from the failed-message total in aggregate reports. No matching index generally means that no RUF report has arrived, not that ParseDMARC failed. MailPosture does not display message samples because they can contain personal or confidential content.

DKIM

Checks each configured selector for a published public key and reports missing, revoked, or weak RSA keys. Selectors must be entered because DNS cannot reliably discover them.

MTA-STS

Checks the DNS signal, HTTPS policy file, policy mode, and whether the policy covers every published MX host.

TLS reporting

Looks up _smtp._tls, requires exactly one TLSRPTv1 policy, validates its syntax, and validates each mailto or HTTPS rua destination. It also summarizes stacked SMTP session results, reporting organizations, and failure types from parsedmarc. The values count SMTP sessions, not messages. Processed reports normally move to Archive/SMTP-TLS; MailPosture reads the normalized OpenSearch data.

SMTP service

Tests each published MX host on TCP port 25 for connection and transaction time, forward-confirmed reverse DNS, a valid host name, banner alignment, STARTTLS negotiation and certificate trust, and unauthenticated relay protection. Results reflect MailPosture’s network location, and the container must be allowed outbound TCP port 25. The relay probe uses reserved example addresses and stops before DATA, so it never sends a message. If the server accepts the recipient from MailPosture’s network, verify from an external network because a locally trusted source can relay by design.

TLS certificates

Connects to configured direct-TLS endpoints, validates trust, and reports days until expiration. SMTP STARTTLS for published MX hosts is tested separately by SMTP service diagnostics.

BIMI

Checks the BIMI record, DMARC prerequisites, HTTPS logo, safe SVG content, and whether a mark certificate URL is published. After validation, the logo appears on the BIMI control card through MailPosture’s same-origin image endpoint. You can independently ignore an intentionally self-asserted logo or intentionally absent logo permanently or for 1–120 months. Invalid records, unsafe logos, and unmet DMARC requirements remain actionable.

IP and domain reputation

Screens the monitored domain and its receiving MX addresses against Spamhaus DBL, Spamhaus ZEN, and SpamCop through DNS. It is not a complete reputation score or a deliverability guarantee. Outbound sending services can use different IP addresses and should be checked separately. An unavailable provider is never reported as clean.

Troubleshooting

System Status and logs

Yellow single-node cluster

A single OpenSearch node cannot place a replica beside its primary shard. System Status separates report, security-audit, internal, and other shards. When every primary and report shard is available, MailPosture labels the pipeline operational and identifies the yellow state as expected replica placement. Use monthly indexes, one shard, and zero replicas for new indexes on a single node. Keep replicas when you operate multiple data nodes.

Report index patterns

The Report indexes card covers all domains because index patterns are shared by the OpenSearch cluster. Expand each pattern to see its matching indexes and document counts. An aggregate or SMTP TLS index should appear after the first matching report is processed. A missing optional RUF index is informational and needs no remedy unless you expected a provider to send one.

Event history

The in-app history records state changes detected by MailPosture for its own checks, OpenSearch, and the ParseDMARC heartbeat. Entries describe what happened at their displayed time and can remain visible after a service recovers. Use the current status cards above for the latest state. The history intentionally excludes secrets, email content, and unrestricted Docker logs.

Service logs

The standalone Compose file mounts recent MailPosture, OpenSearch, and ParseDMARC log files read-only into MailPosture. The viewer uses a fixed service list, limits output size, and redacts common secret labels. Logs can still contain domain names, IP addresses, and message metadata, so review them before sharing. External deployments must provide equivalent read-only mounts or leave this feature disabled.

Source host names

For failing DMARC sources, MailPosture first uses names and network ownership saved by parsedmarc, then attempts a reverse-DNS lookup. A missing name is normal when the address owner does not publish a PTR record. Treat a host name as supporting context, not proof of identity.

Terms

Glossary

Alignment
The authenticated SPF or DKIM domain matches the domain visible in the message’s From address according to DMARC rules.
Selector
The label identifying a DKIM public key, such as selector1._domainkey.example.com.
Policy
DMARC uses none, quarantine, or reject. MTA-STS uses none, testing, or enforce.
RUA
The address that receives aggregate DMARC or TLS reports.
RUF
The optional address that receives individual DMARC failure or forensic reports. Provider support is limited, and these reports can contain sensitive message data.
MX
A DNS record identifying the servers that receive email for a domain.
TLS endpoint
A host and port that presents a certificate directly, such as mail.example.com:465.
Posture score
A summary indicator weighted by control status. It helps prioritize work but does not replace the evidence shown for each check.

What MailPosture changes

MailPosture reads public DNS, HTTPS and TLS endpoints, and OpenSearch report data. SMTP diagnostics open a session to each published MX host and send only EHLO, MAIL FROM, RCPT TO, RSET, STARTTLS, and QUIT commands using reserved example addresses; they never send DATA or message content. In the standalone deployment, saving Settings writes parsedmarc’s active configuration, triggers an automatic parsedmarc reload, and manages the OpenSearch snapshot policy. parsedmarc—not MailPosture—moves report messages into its Archive subfolders.
